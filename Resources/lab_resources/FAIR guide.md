# FAIR guide — what the vault does for you, and what you do

FAIR = **Findable, Accessible, Interoperable, Reusable** (Wilkinson et al., *Scientific Data*
2016; summary at https://www.go-fair.org/fair-principles/). The principles apply to data **and
metadata** — your notes are the metadata of your experiments. FAIR does not mean "open": data can
be FAIR and still restricted (see A1.2 and the [[CARE guide]]).

The table maps each of the 15 FAIR sub-principles to the vault feature that supports it and to
the habit that makes it work.

| # | Principle (GO FAIR wording, shortened) | Vault feature | What you do |
|---|-----------------------------------------|---------------|-------------|
| F1 | (Meta)data get a globally unique, persistent identifier | Lab-wide IDs `EXP-/SMP-/MAT-/PRT-/DATA-/CODE-<INI>-YYYYMMDD-NN`, generated by *New experiment* / *New record*, never changed | Always create records with the commands; quote the ID on tubes, slides, figure legends, file names |
| F2 | Data are described with rich metadata | Typed properties + type-specific parameter tables in 32 experiment templates; schema in `Resources/lab_resources/schema/note-types.json` | Fill the properties and parameter table, not just free text |
| F3 | Metadata include the identifier of the data they describe | Data references carry `location`, `persistent_id`, `checksum`; experiments link them in `data_refs` | Register every raw dataset as a DATA- note and link it |
| F4 | (Meta)data are registered in a searchable resource | Experiment index, Data register, Samples, Materials, Protocols, Template register (Bases views), core search | Keep notes in their folders; check indexes before creating duplicates |
| A1 | Retrievable by identifier with a standard protocol | Plain Markdown + wikilinks; data references point to paths/URLs/DOIs/accessions | Use resolvable locations (server paths, HTTPS, DOIs, SRA/EGA accessions) |
| A1.1 | The protocol is open and free | Plain files, Git over HTTPS, no proprietary format | Nothing extra |
| A1.2 | Authentication/authorisation where necessary | Private Git repository per student; `confidentiality`, `access_conditions` | Keep your repository private; state who may access each dataset |
| A2 | Metadata stay accessible when data are gone | DATA- notes remain after raw data are archived, moved or deleted | Update `location`/`status` instead of deleting the note |
| I1 | Formal, shared language for knowledge representation | ISO 8601 dates, SI units, a documented YAML subset, JSON Canvas, Markdown tables | Use the Properties panel; dates as YYYY-MM-DD |
| I2 | Vocabularies that are themselves FAIR | Template prompts for NCBI Taxonomy, HGNC/Ensembl, UniProt, ChEBI/PubChem, Cellosaurus/RRID, UBERON, OBI, DOI/PMID | Paste the identifier, not just the common name (e.g. `CVCL_0023`, `CHEBI:27899`) |
| I3 | Qualified references to other (meta)data | Typed link properties: `samples`, `materials`, `protocols`, `parent_sample`, `supersedes`, `data_refs`, `code_refs`, `projects` | Link records in properties, not only in text |
| R1 | Richly described with accurate, relevant attributes | FAIR core in every experiment: aim, materials with lot numbers, deviations, observations, outcome incl. **failed/negative** | Record what actually happened, including what went wrong |
| R1.1 | Clear data-usage licence | `license` property on every note (default `lab-internal`, e.g. `CC-BY-4.0` when shared) | Set the licence before sharing or depositing |
| R1.2 | Detailed provenance | `template_id`/`template_version`, cited protocol **version**, progress log linking daily notes, Git history | Log work the day it happens; keep the cited protocol version |
| R1.3 | Meets domain community standards | MIQE fields (B3 RT-qPCR), ARRIVE-aligned fields (E1/E2), MIxS-aligned fields (F3), sequencing metadata for SRA/EGA | Use the specific template, not the generic one, when it exists |

In this edition the PI's reviewed sign-off, committed under their own Git identity, adds a verified
provenance step to R1.2.

## Five habits that make your notes FAIR

1. **Start every day in the daily note**, and create structured records from there with the commands.
2. **Identify things**: IDs on everything you create, persistent identifiers for things others made.
3. **Link, don't copy**: link samples, materials, protocol versions and data references in properties.
4. **Keep raw data where it belongs** and register it ([[Data capture guide]]).
5. **Record versions**: protocol version, software versions, code commit, template version (automatic).

## How this relates to OKF

FAIR asks that records can be *found and reused*; the **Open Knowledge Format** (OKF) is one
concrete way of writing them so other tools and AI agents can read them without rewriting. Your
notes already follow OKF's rules (properties with a `type` in every note). The three properties
OKF recommends support FAIR directly: `title` and `description` make a record findable and
understandable on its own (F2, R1), `tags` add cross-cutting facets (F4). Fill the one-sentence
`description` when an experiment is finished. Details, the export and a worked example: [[OKF guide]].

## Checking yourself

Open *Vault Health* in Obsidian, or run the validator on a computer with Python:

```text
python Resources/tools/validate_vault.py
```

It reports missing properties, broken links, unregistered large files, incomplete data
references and missing CARE / ethics fields — each with a suggestion.
